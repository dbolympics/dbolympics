# <img src="docs/logo.svg" height="40" alt=""> DB Olympics

A realistic, join-heavy database benchmark. It has two parts:

- **Data:** a deterministic simulator of *Tidewick Commerce*, a multi-tenant e-commerce
  platform (shops, orders, payments, shipping, support, marketing, analytics, ...). It
  writes 251 tables as Parquet.
- **Queries:** 409 analytical queries, written by LLM agents role-playing the company's
  managers, analysts and engineers. Each query can be traced back to the conversation that
  led to it.

## Running the benchmark

`dbo-bench` (in `bench/`) runs each system on each configuration of a benchmark file,
`bench/benchmark_sf<sf>.toml` (scale factor, threads, memory, timeout): it generates missing
data, starts the system in containers, loads everything through 2024, runs all queries, then
loads 2025 quarter by quarter, running the queries after each load, and checks the last run's
results against the references ([docs/RUNNER.md](docs/RUNNER.md)).

```bash
bench/host-setup.sh                 # once per machine, needs sudo
cargo build --release --workspace   # builds dbo-bench and the generator, dbolympics
./target/release/dbo-bench run --benchmark bench/benchmark_sf1.toml   # or with --system duckdb
```

Median times go to `systems/<system>/results/<date>/<config>.csv`, what ran to
`<config>.json` next to it; raw timings, results and logs to `bench/out/<date>/<config>/<system>/`,
kept only if the run failed or with `--keep`.

## Adding a system

A system is a self-contained directory `systems/<name>/`; the runner builds a container image
from it and does the rest (schema, loads, queries, timing, checking).

| File | Purpose |
|---|---|
| `system.toml` | the load statement for a Parquet file, the SQL spellings that differ, session settings, extra containers, the name the website shows |
| `install` | installs the system and builds the query program; runs once, when the image is built |
| `start`, `stop` | start and stop the system's servers and the query program |
| `query.rs` | a small Rust program that keeps one connection to the system and runs each statement it gets, unchanged |
| `logo.svg` | optional: the system's mark on the website |

Start from the closest system: `postgres`, `cedardb` (PostgreSQL protocol), `clickhouse`,
`firebolt` (HTTP), `duckdb`, `datafusion` (embedded). Then:

```bash
./target/release/dbo-bench render --system <name> --out rendered/<name>   # the SQL it will get
./target/release/dbo-bench run --benchmark bench/benchmark_sf1.toml --system <name> --keep
```

Same schema for everyone, the system loads the Parquet files itself, dialect differences go in
`system.toml`, no result caches. Guide and rules: [docs/VENDORS.md](docs/VENDORS.md).

When it runs, send the directory as a pull request; a maintainer has it benchmarked on our server by commenting
`/benchmark` ([docs/BOT.md](docs/BOT.md)). **We run the published results ourselves**
on one server (AMD EPYC 9745, 128 cores / 256 threads, 1 TiB DDR5, Linux 7.0) standing in for
AWS c8a instances: a configuration gets the first hardware threads, as many as the instance has
vCPUs, and the instance's memory.

## Generating data

`--sf` is the scale factor (about 1 GB of CSV-equivalent data per unit):

```bash
./target/release/dbolympics generate --sf 1 --out data/sf1
```

| Scale factor | Rows | Parquet | Generation time |
|---|---|---|---|
| 1 | 6.1 M | 0.2 GB | seconds |
| 10 | 45.5 M | 1.7 GB | ~15 s |
| 100 | 411 M | 15.5 GB | ~2 min |
| 1000 | 4.1 B | 151 GB | not measured |

- **Deterministic output:** the same `--sf` and `--seed` (default 42) give byte-identical
  files, whatever the number of threads (`--threads`, default: all cores).
- **Scaling:** shoppers, orders and events grow with the scale factor; the 120 merchants,
  the catalogs and the reference tables do not.
- **Output:** per table `2024-and-earlier.parquet`, then `2025-Q1` ... `2025-Q4`
  ([docs/SIMULATOR.md](docs/SIMULATOR.md), Output).

```bash
./target/release/dbolympics validate data/sf1       # load with all constraints, run the rule checks
./target/release/dbolympics measure data/sf1        # rows and bytes per table
./target/release/dbolympics check-periods data/sf1  # rows and bytes per period, prefixes complete
```

## Loading the data

The schema is in [`schema/`](schema/): `schema/schema.json`, and DDL for DuckDB, Postgres and
standard SQL in `schema/ddl/`, generated by `python3 tools/emit_ddl.py --all`.
`dbolympics load data/sf1 data/sf1.duckdb` builds a DuckDB database; other systems load the
Parquet files directly. Text must compare by code point (binary collation); for Postgres (17
or later) that is the builtin `C.UTF-8` locale:

```sql
CREATE DATABASE sf1 TEMPLATE template0 ENCODING 'UTF8' LOCALE_PROVIDER builtin BUILTIN_LOCALE 'C.UTF-8';
```

## The queries

[`workload/queries/q001.sql` ... `q409.sql`](workload/queries/) are standard SQL wherever that
makes no difference to performance, with `{{...}}` placeholders where databases need different
spellings (e.g. `{{year_month(x)}}`). Every query returns the same rows in the same order on
every database, with tie-breakers added where needed
([docs/QUERY-GENERATION.md](docs/QUERY-GENERATION.md), "Determinism review").
`workload/queries/derivations.json` lists how each was derived from the agents' SQL.

Render the queries for one database (its spellings are the `[dialect]` section of its
`system.toml`, see [docs/RUNNER.md](docs/RUNNER.md), Dialects):

```bash
./target/release/dbo-bench render --system duckdb --out rendered/duckdb
```

It writes `qNNN.sql`, `schema.sql` and `settings.sql` (session settings to run first).

**Provenance:** [`workload/catalog.json`](workload/catalog.json) has each query's original
SQL, business question, related queries and trace into the role-play run, archived with
transcripts in [`runs/`](runs/README.md).

## Query results

**Reference results** for SF1, SF10, SF100 and SF1000 are in
[`workload/results/`](workload/results/) (`sf<sf>/through-2025-Q4/qNNN.csv`, everything
loaded): CSV without a header, rows in query order, NULL as an empty field, numbers exact.
They come from Umbra with exact arithmetic, cross-checked against DuckDB and Hyper;
`MANIFEST.json` records the scale factor, the engine and the run. To check results by hand
(the runner does this itself), write them as headerless `qNNN.csv` and compare:

```bash
./target/release/dbo-bench check workload/results/sf1/through-2025-Q4 my-results/
```

It compares values in order, with a small numeric tolerance; the rules and how the
references are made: [docs/NUMERICS.md](docs/NUMERICS.md).

## The website

`site/` builds the static website (results, methodology, one page per query with its role
play) into `site/out/`, not checked in; serve it with any web server.

```bash
python3 site/extract.py && python3 site/build.py && python3 site/queries.py --raw
```

`runs/index.html` browses the raw role-play run (written by `tools/roleplay_viewer.py`).
